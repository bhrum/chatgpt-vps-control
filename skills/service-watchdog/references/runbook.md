# Runbook: device disappears from ChatGPT's device list

## Symptoms

`list_devices` in ChatGPT no longer shows `htch-runtime` as online (or does
not list it at all).

## Diagnose

```bash
systemctl is-active chatgpt-computer-control
ls -la /etc/systemd/system/chatgpt-computer-control.service
journalctl -u chatgpt-computer-control --no-pager | tail -20
```

Common causes, in order of likelihood on this host:

1. **Reboot wiped `/etc`.** Check `uptime` / `journalctl --list-boots`. If the
   unit file is missing but `~/workspace/chatgpt-vps-control` and
   `~/.chatgpt-computer-control` are intact, this is it. Tell-tale sign from
   the 2026-09-28 incident: `/etc/apt/sources.list.d/ubuntu.sources` had also
   been regenerated by cloud-init (the removed `mirror.cogentco.com` entry was
   back), while apt-installed packages in `/usr` survived.
2. **Reboot wiped apt-installed desktop deps (NEW, seen 2026-09-30).**
   Unlike the 2026-09-28 reboot, this one also removed the apt packages
   `xfwm4`, `xdotool`, `wmctrl`, `x11-utils`, `python3-pyatspi`,
   `at-spi2-core` from `/usr`. Symptom: the service is `active` in the
   restart loop but `journalctl` shows `Managed Linux desktop requires
   xfwm4` (or `xdpyinfo`) and it exits immediately, over and over.
   Reinstalling the unit file alone does NOT fix this — the deps must be
   reinstalled first. The installer script
   (`scripts/install-systemd-service.sh`) now handles both; always use it
   rather than restoring the unit by hand.
3. **Host egress proxy down.** The agent logs `ECONNREFUSED` to
   `198.19.0.1:3128` (a.k.a. `hatch-egress-proxy:3128`). Test from the VM:
   ```bash
   timeout 5 bash -c 'echo > /dev/tcp/198.19.0.1/3128' && echo UP || echo DOWN
   ```
   This is host-side infrastructure and cannot be fixed from inside the VM.
   The service keeps retrying (`Restart=always`); the agent reconnects on its
   own once the proxy is back. Seen 2026-09-28 01:05–06:12 after a reboot;
   recovered without intervention.
3. **Stale proxy credentials.** If logs show HTTP 407, something baked a
   rotating credential into a file. The fix is the credential-less URL
   `http://hatch-egress-proxy:3128` (see `scripts/run-service.sh`).

## Manual recovery (one command)

```bash
sudo ~/workspace/chatgpt-vps-control/scripts/install-systemd-service.sh
```

Then verify:
```bash
systemctl is-active chatgpt-computer-control
journalctl -u chatgpt-computer-control --no-pager | grep "Device agent connected" | tail -1
```

No re-enrollment is needed: device credentials persist in
`~/.chatgpt-computer-control/.env`. Never print them.

## What the watchdog covers

The `device-service-watchdog` hook (see `SKILL.md`) polls every 60 s and runs
the installer when the service is down. The installer now restores BOTH the
unit file and the apt desktop dependency set, so the hook auto-heals causes
1 and 2 above. It does not (and cannot) fix cause 3; it stays silent while
the agent retries and wakes a worker only if the reinstall itself fails.

## Verified history

- 2026-09-28: VM reboot wiped the unit file; manual reinstall restored the
  device. Watchdog hook installed and live-tested (service stopped → hook
  restored it in seconds).
- 2026-09-28 01:05: real reboot test. Watchdog reinstalled the service ~1 min
  after boot. Egress proxy was down 01:05–06:12 (host-side); agent reconnected
  automatically at 06:12 with no manual action.
- 2026-09-30: reboot wiped the unit file AND the apt desktop deps (`xfwm4`,
  `xdotool`, `wmctrl`, `x11-utils`, `python3-pyatspi`, `at-spi2-core`).
  Service stuck in auto-restart death loop (`Managed Linux desktop requires
  xfwm4 / xdpyinfo`); the watchdog's unit-only reinstall could not fix it.
  Watchdog worker reinstalled the deps via apt; service auto-restarted and
  reconnected at 23:18 (previous day). Installer script updated to reinstall
  the dep set before enabling the service, so the watchdog now self-heals
  this case too.
